# 0.8.276 — The command registry, and a sitemap that tells the truth (2026-10-09)

Phase 2 of the command-registry plan, plus a search-engine bug that had been live for several
releases.

## Highlights
- **The command palette says why a command is unavailable** instead of doing nothing when you
  click it — "Select two or more objects" under a greyed **Group**.
- **Every palette command is one named undo step**, and undoes itself cleanly if it fails.
- **`Yappy.commands`** — everything the app can do, as data a script can list and run.
- **Sitemap dates are real again.** Every page had been claiming to change on every deploy.

## Features
- **`Yappy.commands.list()`** returns every command: id, label, category, shortcut, and whether
  it can run right now (`enabled: true`, or a string saying what it needs). **`run(id, params?)`**
  is the single way in — the same one the palette uses — so a scripted command is one labelled,
  atomic undo step that rolls back on failure, exactly as a clicked one is. **`aliases()`** maps
  the old palette ids to the new namespaced ones.
  ```
  Yappy.commands.list().filter(c => c.enabled !== true);   // what's unavailable, and why
  Yappy.commands.run('action.group');   // → { ok: false, reason: 'Select two or more objects' }
  ```
- Command ids are namespaced (`action.group`, `tool.lasso`). **The old ids keep working** as
  aliases, so anything that stored one is unaffected.
- Unavailable commands are shown greyed with their reason rather than hidden. Reading "Select
  two or more objects" is how you learn what Group needs; a row that has vanished teaches
  nothing.

## Fixes
- **#429 Every sitemap URL carried the same `lastmod`** — the release date, on every deploy.
  Live for at least four releases. `prerender.ts` reads each page's real commit date, and its
  own comment explains the stakes: a crawler that sees every page change daily and finds them
  identical learns to ignore the field. **The lookup is correct; the deploy architecture
  defeated it.** Hostinger builds the OSS mirror, whose history is one squashed sync commit per
  release touching every file, so `git log -1` returned the release date for everything. Dates
  are now computed in the source repo, where history is real, and shipped to the mirror as
  data. The live sitemap carries 15 distinct dates across its 42 URLs.
  Nothing failed while this was wrong: the sitemap validated and `verify:deploy` passed, because
  it checks the sitemap is *served*, not that its contents say anything.

## Internal / tests / docs
- `frontend/src/commands/` — `registry.ts`, `execute.ts` (resolve → validate → check → one
  history transaction → run → roll back on throw), `ui-port.ts`, `adapt-palette.ts`. No
  component imports, so the registry and `execute` run under `bun test` with no DOM.
- Commands are **adapted** from the existing palette list rather than re-declared: 142 new
  literals duplicating already-translated definitions would be 142 chances to mistype an id or
  a store call, found only when someone clicks the one command nobody tested.
- Ids are **derived** (`action-new-artboard` → `action.newArtboard`), with a test that the
  derivation is injective across the real id set — two ids collapsing onto one would throw on
  registration and silently lose a command.
- Per-layer palette entries stay out of the registry: `getCommands()` is a live projection, not
  a list, and `layer-3f2a…` is data rather than capability. The palette still lists them.
- `scripts/build-lastmod.mjs` walks history **once** (`--name-only`, newest-first, first
  sighting wins) for exactly the sources the sitemap asks about. `npm run build:lastmod`.
- 20 new unit tests (headless) and 9 new e2e for the registry; 7 for the lastmod map, including
  the one that matters — **the dates must not all be the same**.
- `docs/command-registry-plan.md` §9 records what P2 shipped and the four places it departed
  from the plan, with the reason for each. P3–P6 remain open.

## Breaking changes / migration
- None. Old command ids keep working as aliases.
