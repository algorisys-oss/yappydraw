# 0.8.184 — Verify the deploy (2026-08-07)

Infrastructure. No product changes: this release adds the check that catches a class of failure
the previous three releases were quietly suffering from, plus a fix for an `.htaccess` rule that
had never actually worked.

## Why

The precache trim shipped in 0.8.181 kept appearing to un-ship itself. Sampling the same URL
eight times explained it:

```
$ for i in $(seq 1 8); do curl -s .../sw.js | grep -c 'url:"'; done
220 220 220 220 220 220 220 178
```

| Response | `last-modified` | Precache | Build |
| --- | --- | --- | --- |
| 7 of 8 | 09:13 | 220 entries | pre-0.8.181 |
| 1 of 8 | 12:10 | 178 entries | current |

Both with `x-hcdn-cache-status: MISS` — so not CDN caching. **The origin itself holds inconsistent
copies.** The asset directory is mixed the same way: a v0.8.180 chunk still returns 200 while a
v0.8.181 one returns 404.

Two consequences. Most visitors have been running a service worker from several releases back, so
the 9.6MB → 4.6MB precache saving never reached them. And it is a strong candidate for the *real*
cause of the "Something went wrong" screen: a visitor can get an `index.html` naming chunks that
the node answering the next request doesn't have — random per request, and fixed by reloading,
which is exactly what was reported.

## What's in this release

### `npm run verify:deploy`

`scripts/verify-deploy.sh [url] [samples]` — run it after deploying:

- **Samples `sw.js` and `index.html` N times (default 8)** and fails if the responses differ. A
  single fetch cannot detect a split origin; that is why the earlier "verified live" check for
  0.8.181 was wrong.
- **Checks every asset `index.html` references resolves** — a 404 chunk *is* the error screen.
- **Asserts the cache headers** from `frontend/public/.htaccess` actually arrived (many upload
  tools skip dotfiles, and the failure looks identical to the original bug).
- Compares the live version against `package.json`.

Exits non-zero, so it can gate a deploy. Added to the "ship it" flow in `CLAUDE.md`.

### The sw.js cache rule now works

The verifier's first run found that `sw.js` was being served with the host's own
`public, max-age=604800`, while the `.html` and hashed-asset rules from the same `.htaccess` were
applying correctly — so that block had never taken effect. Most likely a host-level `mod_expires`
rule for JavaScript overwriting `mod_headers`, since mod_expires runs later. Rewritten as an exact
`<Files "sw.js">` with `Header always set` plus `ExpiresActive Off` for that file.

A cached service worker delays every update by however long the cache says — browsers cap SW
script caching at 24h, but that is still a day of serving a build we have replaced.

## Action required on the host

This release makes the problem visible; it cannot fix it from inside the repo. If
`verify:deploy` reports a split build, the upload is merging rather than replacing. Re-deploy so
the remote tree is replaced:

- `rsync -av --delete dist/ user@host:/path/public_html/`
- FTP: delete the remote `assets/` directory first, or use a client set to delete files not in
  source
- Panel deploys: clear the site's build/CDN cache afterwards
