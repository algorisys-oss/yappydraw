# 0.8.257 — selecting a mindmap node no longer recolours its child (2026-09-15)

## Highlights
- **A mindmap child keeps its colour when you select its parent.** Selecting a node could paint the
  node drawn after it, usually its newest child, solid green until you clicked away.

## Features
- None.

## Fixes
- **#371: selecting a mindmap parent turned its child's fill green.** The selection chrome is drawn
  between one element and the next. The quick-connect buttons, drawn for a single selection, left
  the canvas fill colour (`#10b981`), stroke colour, line width and shadow set, and the following
  element's fill could inherit them. `renderElementOverlays` now saves and restores the canvas state
  around the whole pass, so no overlay block can leak into the next element.

## Internal / tests / docs
- **New test:** `frontend/src/utils/selection-overlay-state.test.ts` drives the overlays with a
  context that really restores state and asserts that the paint state is unchanged afterwards (single
  selection, hovered quick-connect button, collapsed node). It failed before the fix.
- **Checked in a browser:** a child's centre pixel matches with the parent selected and deselected,
  in both sketch and architectural styles.
- **Open question:** the reported document's child took a fill path that reads the inherited colour,
  and which style causes that was not identified. A colour the canvas cannot parse reproduces it.
- **Docs:** bug log #371 and a learnings entry on shared canvas paint state. No help, hotkey or
  `api.ts` changes.

## Breaking changes / migration
- None.
