# 0.8.275 — Undo that keeps your place, and names its steps (2026-10-08)

Phase 1 of the command-registry plan (`docs/command-registry-plan.md`). The six open design
decisions are settled; P1 was deliberately scoped to depend on only two of them, so the
user-visible wins land without committing to the registry's architecture.

## Highlights
- **Undo no longer deselects everything.** Undoing an edit puts back whatever was selected
  before it. This is the one people feel on every single undo.
- **The History panel names the steps.** "Group", "Scatter" — rather than "State 7" — for any
  action that runs as a command.
- **A script action can be one named, atomic undo step** that rolls itself back if it fails:
  `Yappy.command('Scatter', fn)`.

## Features
- **`Yappy.command(label, fn)`** — run `fn` as one named undo step. It is **lazy** (a function
  that turns out to edit nothing leaves no history entry at all), **collapsing** (however many
  internal edits it makes, it is one undo), **nesting** (an inner command joins the outer step)
  and **atomic** (if it throws, the document goes back exactly as it was and the error
  propagates — no half-finished edit to clean up). Sync or async.
  ```
  Yappy.command('Scatter', () => {
    for (let i = 0; i < 50; i++) Yappy.createCircle(i * 14, 0, 12, 12);
  });
  Yappy.undoLabel();   // 'Scatter'
  ```
- **`Yappy.historyEntries()`**, **`undoLabel()`**, **`redoLabel()`**, **`withoutHistory(fn)`** —
  the undo timeline and its step names, for a script or a custom panel.
- Undo and redo restore the selection, filtered to ids that still exist on a visible, unlocked
  layer, falling back to empty.

`Yappy.batch` is unchanged and is a different tool: it groups edits and coalesces the reactive
update, but it always records a step (even when nothing is edited), does not name it, and does
not roll back. The two now cross-reference each other in the docs; reach for `command` when you
are performing one action a person would name.

## Internal / tests / docs
- The migration's cheap trick: **none of the ~366 existing `pushToHistory()` call sites change.**
  They became transaction-aware instead — inside a command the first push records an entry and
  the rest collapse into it; outside one, behaviour is byte-identical with a null label. When a
  change looks like 366 edits, the question is what single function they all go through.
- `HistoryEntry extends HistorySnapshot { label, selection }`. In-memory only — nothing here
  reaches a saved file, and no file format changed.
- `tests/history-transactions.spec.ts` — 11 tests: collapsing, a no-op command leaving no entry,
  sync and async rollback, nesting, selection restore on undo and redo, stale-id filtering,
  labels, legacy pushes unchanged, `withoutHistory` inside a command. All 11 fail without the
  change.
- Two of those tests originally passed against unfixed source — `Yappy.command` was undefined,
  the `TypeError` landed in the test's own bare `catch {}`, and every assertion held vacuously.
  The A/B run caught it; they now assert the error message rather than that something threw.
- `docs/command-registry-plan.md` §9 records the settled decisions and what P1 delivered against
  the spec. P2–P6 (registry core, command sweep, keymap, generated help, public command API)
  remain open.

## Breaking changes / migration
- None. Undo keeping the selection is a behaviour change users will notice, and is the point.
