# 0.8.273 — The build's memory headroom is now a number (2026-10-08)

Internal release: build tooling and test plumbing. No user-facing change, so there is no
"What's new" entry for it.

## Highlights
- **`npm run build:memory`** runs the production build under a memory sampler, prints the peak,
  and fails past a budget. The first measurement found CLAUDE.md's recorded figure was wrong by
  about 400 MB — not from a regression, but because it was written down once and the bundle kept
  growing.
- **`npm test`** exists. There was no test script at all.

## Features
- `npm run build:memory` — samples `/proc` VmRSS across the build's whole descendant set every
  200 ms, reports the peak total, the largest single process in it and the wall time, and exits
  non-zero past a 2400 MB budget. `BUILD_MEM_BUDGET_MB` overrides the budget; a trailing command
  overrides what it measures. Non-Linux platforms report that and exit 0 rather than blocking a
  release.
- `npm test` — `bun test frontend scripts`, the whole unit suite in one documented command.

## Fixes
- **#426 Nothing measured the build's peak memory, and the recorded figure had drifted ~400 MB.**
  CLAUDE.md said the `--max-old-space-size=1536` cap "keeps the peak at ~1.65 GB". Measured over
  four runs: **2013-2084 MB** of tree RSS, largest single process (vite's main thread)
  **1740-1798 MB**. This is the risk CLAUDE.md names in advance — "the peak still climbs release
  by release, and nothing measures it, so the next ceiling arrives as an outage" — and it has
  already arrived twice on the host (#344, then v0.8.236/237).
- **#427 There was no `npm test`**, so a unit test added outside `frontend/` would be run once by
  its author and never again, this repo having no CI. A bare `bun test` can't serve as the
  command: it sweeps in the Playwright specs and reports all of them as failures.

## Internal / tests / docs
- Measures the process **tree**, not one process: four are alive at the peak, and the figure that
  gets a build OOM-killed is the concurrent total. `/usr/bin/time`'s `ru_maxrss` reports the
  largest single reaped child instead — close enough to mislead.
- Separates the two failure modes in its own output: "killed at the ceiling" (bug #344's no-logs
  OOM signature) versus "exited non-zero with memory to spare, so memory is NOT the cause — read
  its own error". That second message is there because v0.8.236/237 was read as OOM when it was a
  plain ENOENT in the prerenderer.
- Deliberately **not** folded into `npm run build`: that script is what Hostinger, the OSS
  `--verify` pass and the desktop build all run, and wrapping it would make the deployed artifact
  depend on the measurement.
- Budget set from measured variance (~3.5% across four runs), not one sample, and raising it
  requires a fresh measured figure in the comment beside it.
- 12 unit tests (`scripts/build-memory.test.mjs`) for the tree-walk and the pass/fail boundary,
  with an unrelated sibling process in the fixture — under-reporting is the dangerous direction,
  since a budget that never trips is worse than no guard. Both runner paths exercised end to end.
- CLAUDE.md: ship step 4 points at `build:memory`, the memory paragraph carries the measured
  figures, and a new **Tests** section documents `npm test` and why a bare `bun test` fails.

## Breaking changes / migration
- None. `npm run build` is unchanged, byte for byte.
