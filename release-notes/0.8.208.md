# 0.8.208 — the deploy check was checking the wrong hostname (2026-08-21)

## Highlights
- `npm run verify:deploy` reported **seven failures on a healthy deploy** because it was
  pointed at a hostname the host has broken. It now checks the canonical host, and reports the
  actual www defect as one precise line instead of as the noise floor for everything else.
- Bug **#280 is genuinely fixed** on the host — `sw.js` returns `no-cache, must-revalidate`.
  `CLAUDE.md` had been telling every session to expect that failure and wave it through.

## Fixes
- **#308 — `verify:deploy` failed against a good deploy.** It defaulted to
  `https://www.yappydraw.com`, and the www hostname answers every URL with a 301 whose
  `Location` has lost the domain: `/help/` → `https://help/`, `/` → `https://`. The path is
  being substituted for the hostname. Nothing in `frontend/public/.htaccess` does this (there
  is no www rule there), so it is a Hostinger control-panel redirect and cannot be fixed from
  the repo. The apex host passes every check and is what the prerendered pages name as their
  canonical, so that is now the default.
- The script's failure epilogue explained split builds and told you to re-deploy — actively
  wrong when the only failure is a DNS-level redirect, and re-uploading would have "confirmed"
  the problem was unfixable. It now says which failures that advice applies to.

## Internal / tests / docs
- New **Alternate hostname** check in `scripts/verify-deploy.sh`: derives the other form of the
  host (apex ⇄ www), follows one request, and fails when the redirect `Location` has a host with
  no dot in it — the exact shape of this bug, and of the `https://` case where the host is
  dropped outright. Non-responding alternates warn rather than fail, so staging URLs and custom
  domains are unaffected.
- `CLAUDE.md` step 9 rewritten: the standing failure is now the www redirect, not the cacheable
  `sw.js`, with the superseded note kept so the old expectation is not silently re-learned.
- Learnings recorded: a check that always fails is a check nobody reads; and content hashes
  compared across two different build trees prove nothing (the live site builds from the cleaned
  OSS copy, so its chunk hashes legitimately differ from a local `dist/`).

## Breaking changes / migration
None. `verify:deploy` still accepts an explicit URL as its first argument; only the default
changed, from the www host to the apex.
