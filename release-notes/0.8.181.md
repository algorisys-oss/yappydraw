# 0.8.181 — The error screen nobody could reproduce (2026-08-07)

Two production problems with one root in common: **caching**. Users were hitting the
"Something went wrong" screen on a build that works, and the app was slow to load for
returning visitors. Neither was a bug in the app's code.

## Highlights

- **The "Something went wrong" screen after a deploy is fixed at the source** — the host was
  sending no `Cache-Control` on `index.html`, so browsers reused a stale copy pointing at chunks
  that no longer existed.
- **Precache cut from 9.6MB to 4.6MB** (220 → 178 entries). Every release used to make returning
  visitors re-download all of it.
- A stale visit now **heals itself** with a single guarded reload instead of showing an error.
- The GoatCounter `ERR_BLOCKED_BY_CLIENT` in the console is **harmless** and was never the cause.

## Fixes

### The error screen

`curl -I` against the live site told the whole story:

| Path | Cache-Control served |
| --- | --- |
| `/` (index.html) | **none at all** |
| `/assets/*.js` | `public, max-age=604800` |
| `/sw.js` | `public, max-age=604800` |

With no freshness directive, browsers apply *heuristic* caching to index.html — typically 10% of
the time since `Last-Modified` — and reuse it without revalidating. Every deploy replaces the
content-hashed chunks and removes the old ones, so a returning visitor asked for
`/assets/index-OLDHASH.js`, got a 404 served as an HTML error page (so the module parse failed
too), and landed on the route ErrorBoundary. Reloading fixed it because a reload revalidates the
document. Shipping several times a day made it frequent.

New `frontend/public/.htaccess` sets the policy the deploy was missing: hashed assets `immutable`
for a year, `*.html` / `sw.js` / `workbox-*.js` / the manifest `no-cache, must-revalidate`.

> **Deploy note:** this only helps once `.htaccess` reaches the site's web root. If your upload
> step skips dotfiles, copy it manually — verify with
> `curl -sI https://www.yappydraw.com | grep -i cache-control`, which should now return
> `no-cache`.

### Self-healing, and an error screen that says something useful

`utils/stale-build.ts` recognises the "this chunk is gone" wordings across browsers — including
the `Unexpected token '<'` shape you get when a 404 HTML page is executed as JavaScript — and
reloads **once**, guarded by sessionStorage so a genuine, reproducible error can never become a
reload loop. It is also attached to `unhandledrejection`, which covers lazy imports fired from a
button (Help, export) that reject outside any error boundary and previously just left the feature
dead.

What still reaches the error screen is therefore a real error, so it now logs to the console with
its stack and displays it, instead of printing only `err.message` and asserting a cause it cannot
know.

### Slow loading

The service worker precached **220 entries, 9.6MB** — including 5.1MB behind a lazy `import()`
that most visitors never trigger: the HTML-player exporter (1.9MB), MathJax's SVG renderer
(1.2MB) and TeX packages, jsPDF, pptxgen, html2canvas, every help doc, the docs search index. And
since filenames are content-hashed, every release invalidated every entry — so each deploy made
returning visitors fetch the whole 9.6MB again in the background. Precache size multiplies by
release frequency; shipping more often was making the app slower.

Those chunks are now excluded from the precache and covered by a `CacheFirst` runtime rule for
`/assets/*` instead (safe: a hashed URL can never change meaning), so they are cached from first
use without being charged to everyone up front.

**220 entries / 9.6MB → 178 / 4.6MB.**

## Breaking changes / migration

None for documents. One behaviour trade-off, the same one already accepted for the Create Outlines
glyph binaries: the **first** use of export-to-HTML/PDF/PPTX, the help pages or LaTeX rendering
while completely offline now needs the network. Everything is cached from then on, and normal
online use is unchanged — verified against the production build (LaTeX 11/11, SVG and player
export passing).
