# 0.8.191 — An eyedropper that picks the actual colour, and Fill-mode marks you can recolour (2026-08-13)

## Highlights
- The colour picker's **eyedropper now picks the exact colour** of the shape you click. It was
  coming back slightly duller on wide-gamut screens.
- A **Fill-mode stroke can be recoloured** after you draw it. There was previously no control for
  its fill anywhere in the Properties panel.

## Fixes

### The eyedropper picked a slightly different colour (#296)
Sampling a `#FF0000` shape returned `#EA3323`. That pair is a signature, not a rounding error:
sRGB red expressed in Display-P3 primaries is exactly `(234, 51, 35)`.

The pipette used the browser's `EyeDropper` API, which samples the **composited screen**. On a
wide-gamut display that framebuffer holds colours in P3, and the API returns the raw value in a
field named `sRGBHex` — so every pick came back re-encoded: right on screen, wrong once written
into a document that means sRGB.

It can't be corrected after the fact, because whether it needs correcting depends on the user's
monitor. So the pick no longer goes through the screen at all: clicking the canvas now reads the
colour **out of the document**, which is exact by construction and works in every browser rather
than only Chromium.

- Click a shape → its fill colour, exactly.
- **Alt+click** → its outline colour.
- Gradients report their first stop.
- Images, pattern and mesh fills, and bare canvas fall back to sampling the rendered pixel from
  our own canvas — whose context is sRGB, so that path is colour-managed too.

The screen eyedropper is still there as a second button (a small monitor icon, Chrome/Edge only)
for sampling *outside* the app, where it is the only option. Its tooltip says it is approximate on
wide-gamut displays.

### Fill-mode strokes were stuck on the colour they were drawn in (#297)
Fill mode commits a freehand stroke as a filled silhouette and bakes the fill colour in at commit
time. The renderer had always honoured `backgroundColor`, so the fill was editable in principle —
but `fineliner` / `inkbrush` / `marker` / `ink` were missing from `backgroundColor`'s
`applicableTo` list, so the Properties panel never drew a **Background** control for a freehand
mark. Nothing anywhere could change it.

What made it read as broken rather than missing: the panel *does* offer **Stroke**, and changing
that recolours only the thin outline drawn on top of the silhouette, leaving the filled body on
its original colour.

A filled stroke now shows **Background** (the filled body) alongside **Stroke** (the outline), and
they are independent. A freehand stroke that isn't filled still doesn't get the control, since it
has no fill.

## Features
- `Yappy.pickColorFromCanvas(cb)` — arm a colour pick; the next canvas click reports the exact
  colour under the pointer.
- `Yappy.getElementPickColor(id, wantStroke?)` — the colour an eyedropper would read off an
  element.

## Internal / tests / docs
- `startColorEyedropper` / `resolveColorEyedropper` / `elementPickColor` in the store; the armed
  eyedropper gains a `mode` of `'style'` (the existing copy-a-whole-style pick) or `'color'`.
- `samplePixelHex` in `canvas.tsx` reads a single pixel from the canvas backing store with
  `getImageData(..., { colorSpace: 'srgb' })`.
- Reuses the `visibleWhen` property-config predicate added in 0.8.190 to gate Background on
  `fillSilhouette`.
- Help docs updated: eyedropper (masks/appearance) and Fill Mode (logo toolkit).

## Breaking changes / migration
None. Existing drawings are unaffected; the Fill-mode fix only adds a control, and the eyedropper
change affects only what a future pick returns.
