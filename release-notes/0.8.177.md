# 0.8.177 — The text editor sits where the text is (2026-08-06)

A fix-only release. Double-clicking a shape to edit its label opened the editor in the wrong
place, and re-wrapped the text once it got there. Both are gone.

## Highlights

- **The editing box opens exactly over the label** — it used to appear up and to the left,
  outside the shape you clicked.
- **Nothing re-flows or re-aligns while you type** — same line breaks, same vertical alignment,
  in the editor and on the canvas.

## Fixes

### The editor opened offset from the shape

`TextEditingOverlay` and `RichTextEditingOverlay` positioned themselves with `worldToScreen`,
which returns **canvas-local** pixels (`clientX/Y` minus the canvas's bounding rect). Both
render as siblings of `.canvas-drop-zone`, and every ancestor up to `<body>` is
`position: static`, so their `top`/`left` resolved against the document instead.

Those two frames are the same only while the canvas fills the window. It doesn't: `handleResize`
insets the canvas by the docked chrome (`marginLeft`/`marginTop` = `--dock-left`/`--dock-top`),
so in the default layout the editor opened **46px left and 52px above** the text it was editing.

Both overlays now use `utils/overlay-transform`'s `worldToWindow` with `position: fixed` — the
same helper the rulers, symmetry axes, artboard frames and node tool were moved to when they had
this bug. It measures the origin from the canvas element (so it tracks window resizes and dock
changes) and supplies the rotation centre, which the previous `store.viewState` path left at 0 —
so editing under a rotated view was wrong as well.

### Labels re-wrapped and re-aligned on double-click

The renderer wraps container text in the shape's **inscribed** width — a circle or diamond gets
0.707 of its box, a banner 0.65, a lightbulb 0.7 — but the editor's textarea wrapped at the full
width. "Circle Label" was two lines on canvas and one in the editor, and because the vertical
padding was derived from the canvas's two-line height, the single line sat half a line low.

That factor table now lives once in `utils/text-utils` as `inscribedTextFactor`,
`containerTextAvailableWidth` and `containerTextWrapWidth`. `measureContainerText`,
`fitShapeToText`, `RenderPipeline.renderContainerText` and the editing overlay all read it, so
the editor wraps where the canvas wraps.

Matching the renderer's box also closed three smaller gaps in the overlay, all of which showed up
as a jump on double-click:

- **`verticalAlign` was ignored** for container shapes — the editor always centred, so a
  top- or bottom-aligned label jumped to the middle.
- **The hand-drawn baseline nudge** (+2px, applied by the renderer) was missing.
- **`textOffsetX` / `textOffsetY`** — the draggable-label offset — was not applied, so a label
  the user had dragged snapped back to the shape centre while being edited.

## Internal

- `inscribedTextFactor` replaces the same shape→factor chain previously written out twice
  (`measureContainerText`, `fitShapeToText`), and the shape-specific `maxWidth` branch in
  `RenderPipeline.renderContainerText` now calls `containerTextAvailableWidth`.

## Verification

Checked in the running app across rectangle, circle (inscribed wrap), a wrapped multi-line label,
a top-aligned label, a standalone text element, a table cell and a rich-text element, at 100% and
at 150% zoom with a non-zero pan — the overlay lands on the canvas text in every case.

`tests/text-autosize`, `table`, `uml-tools`, `rich-text-lists`, `bpmn`, `mindmap-inherit`,
`sequence-diagram`, `quick-toolbar-fontsize` and `symbol-edit` pass. Two failures
(`text-autosize.spec.ts:48`, `uml-tools.spec.ts:145`) reproduce identically on the unmodified
tree — they are environment-related (toolbar buttons off-screen at this viewport size), not
regressions.

## Breaking changes

None.
