# 0.8.167 — The first diagram in a page is measured against the real font (2026-07-31)

## Highlights
- The first diagram imported into a freshly-loaded page came out a few percent wider than the
  same source imported again later. Text shapes are auto-sized from the measured text **at
  creation**, and on a cold page the webfonts had not actually arrived — so fallback-font
  metrics were baked into the saved document. Measured: 180.39px vs 187.00px for one label, a
  **3.7% error**, permanent rather than a momentary mis-draw.
- The cause is a browser API that reads as ready when it isn't: `document.fonts.ready` resolves,
  and `document.fonts.status` reads `"loaded"`, while `document.fonts.check()` for the font you
  are about to measure with is still **false**.

## Features
- **`Yappy.fontsReady()`** — resolves once the built-in webfonts are usable for measurement.
  Await it before creating text-bearing elements from a script or an embed.
- **`Yappy.fontsLoaded()`** — the same state as a synchronous boolean.

## Fixes
- **Webfonts are now requested at boot.** `document.fonts.ready` only settles the faces that
  have actually been *requested*, and a family that reaches the page through the Google Fonts
  `<link>` is not requested until something first renders with it — so every obvious readiness
  guard agreed the fonts were present while the measurement silently used the fallback. New
  `utils/font-loading.ts` calls `document.fonts.load()`, which is the call that forces the
  request, for every built-in family × {400, 700, italic 400, italic 700}, and `index.tsx`
  fires it at boot. Fire-and-forget: a blocked or offline font degrades to fallback metrics
  rather than stalling boot or breaking an export.
- **`scripts/render-dsl.mjs` awaits the fonts before `importDSL`**, so a batch render no longer
  has to warm the cache by rendering once and throwing the result away.

## Internal / tests / docs
- Verified headlessly, A/B against the pre-fix tree (the boot preload disabled, then restored
  and confirmed byte-identical):

  | probe | pre-fix | fixed |
  |---|---|---|
  | `document.fonts.check('28px Handlee')` after `fonts.ready` | **false** | true |
  | `measureText("AbstractFactory")` on a cold page | **180.39px** | 187.00px |
  | geometry baked by the first import | **166×90** | 150×109 |

- Help doc (`help-docs/features/embedding-doc.tsx`) covers `fontsReady()` in both the
  same-origin and postMessage snippets, with the `document.fonts.ready` trap called out.
- `docs/learnings.md`: readiness APIs for lazily-fetched resources report on the requests that
  were made, not on the resource — and when a measurement is *persisted* rather than merely
  drawn, it needs the same up-front rigour as any other write.
- **Known issue, logged not fixed** (`docs/bugs/bug-fixes.md`): a page whose first import ran
  cold cannot recover by re-importing. `clear()` + re-import reproduces the cold geometry
  exactly even after the fonts demonstrably arrive (probe recovers 180.39 → 187.00; the boxes do
  not). A fresh canvas context re-measures correctly and the shared measurement context was
  ruled out, so sizes are not being recomputed on the second import at all. The boot preload
  makes this unreachable on the normal path. Root cause still open.
- This shipped without a committed regression test; the verification was a throwaway headless
  probe. Worth landing as a spec.

## Breaking changes / migration
None. `fontsReady()` / `fontsLoaded()` are additive, and the preload is fire-and-forget.
