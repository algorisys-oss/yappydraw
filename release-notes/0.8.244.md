# 0.8.244 — The keyboard can no longer go quiet (2026-09-12)

## Highlights
- **Fixes a session-long keyboard lockout.** <kbd>Delete</kbd> stops working, and so does
  every other single-key shortcut — the arrow nudges, the tool letters, <kbd>F2</kbd>,
  <kbd>Enter</kbd>, <kbd>Tab</kbd>, hold-<kbd>Space</kbd> to pan. Nothing on screen explains
  it and only a reload clears it. Introduced in v0.8.242.

## Features
- None. This release is a fix.

## Fixes
- **#361 — the mid-drag guard could outlive the drag and kill every single-key shortcut.**
  Reported as "did we break the delete key?": <kbd>Ctrl</kbd>+<kbd>A</kbd> selects
  everything and <kbd>Delete</kbd> does nothing; select one shape, <kbd>Delete</kbd>,
  nothing.

  v0.8.242 made the single-key shortcut chain inert while a pointer gesture is in flight
  (#360, where brushing a key mid-drag stranded the drag). It decided that from
  `isDrawing || isDragging || isSelecting` alone — flags the tool handlers set on
  pointer-down and clear on the pointer-**up** branch that finalises the gesture. A gesture
  that never reaches its branch strands one, and nothing on the mouse path ever clears it
  again: `selectionOnUp` resets `isDragging`/`isSelecting` but never `isDrawing`, and both
  self-heals for `isDrawing` are on the touch path. The guard then answered "busy" for the
  rest of the session, with <kbd>Delete</kbd> merely the first casualty anyone notices.

  The probe is now gated on a pointer being *physically* down: a set of pointer ids that the
  browser's own `pointerdown` / `pointerup` / `pointercancel` events maintain, with
  window-level listeners for a release the canvas never sees (pointer capture can fail — it
  is in a `try`/`catch` for iPad; a button let go outside the window reports to the window)
  and a `blur` listener for a window that loses focus mid-drag. A physical pointer cannot get
  stuck the way a derived flag can, so the guard is structurally unable to outlive the
  gesture. During a real drag a pointer is always down, so #360 stays fixed.

## Internal / tests / docs
- `tests/hotkeys.spec.ts` — "a lost pointer release cannot deaden the shortcut chain".
  A/B verified: it fails on the pre-fix tree at the `__canvasPointerBusy()` assertion
  (`true`, expected `false`). The #360 mid-drag test still passes alongside it.
- Logged as #361 in `docs/bugs/bug-fixes.md`, with the general lesson in `docs/learnings.md`:
  **a guard that suppresses input must fail open.** Wrong in the "allow" direction gives back
  the original bug, visibly, on one gesture; wrong in the "suppress" direction gives a dead
  keyboard with no error, no log line and no user-reachable reset. Gate on what the browser
  itself maintains, not on state owned by another handler and cleared on the happy path only.
- A related gap is left as-is on purpose and recorded rather than patched: the mouse path has
  no self-heal for a stranded `isDrawing` at all. That is a stroke-start concern, and the
  point of this fix is that the keyboard must not depend on it either way.
