# 0.8.235 — The build stops running out of memory on the deploy host (2026-09-04)

## Highlights

- **The production build no longer exhausts Node's heap.** v0.8.234 failed to deploy: the host
  reported "Build failed" with *no logs at all*, and `vite build` was being OOM-killed at
  ~2.2 GB. Capping V8's heap for that step brings the peak to **1.65 GB** and the build
  completes.
- **Byte-identical output.** Every chunk in `dist/assets` was fingerprinted from a capped and an
  uncapped build and matched, so this changes how the build runs and nothing about what ships.
- No user-facing change. v0.8.234's Dev Mode work reaches the live site with this release.

## Fixes

- **#344** — the Hostinger build of v0.8.234 died with `FATAL ERROR: Ineffective mark-compacts
  near heap limit — JavaScript heap out of memory`. Not caused by that release: measured on
  clean clones, v0.8.233 peaked at **1.88–2.14 GB** and v0.8.234 at **2.17–2.24 GB** — two
  ranges overlapping inside the run-to-run variance of a single version. The build had been one
  unlucky run from failing for several releases, with nothing measuring it.

## Internal / tests / docs

- `npm run build` now invokes vite as
  `node --max-old-space-size=1536 node_modules/vite/bin/vite.js build`. `node` is called
  directly rather than via an inline `NODE_OPTIONS=` prefix, which would not work on Windows.
  Only `vite build` is capped — `tsc -b` peaks at 1.13 GB and prerender at 0.30 GB, neither
  close to the limit.
- The floor was measured rather than guessed: 1024 MB and 768 MB both still OOM, so ~1.3 GB of
  heap is the genuine requirement and 1536 is headroom, not a lucky number.
- `docs/learnings.md` — why an empty build log is itself the diagnosis (a SIGKILLed process
  cannot write an error, which narrows the field to things that *kill* rather than *fail*), and
  why a single sample of a noisy quantity is a story rather than a measurement.

## Known / not fixed

The reason the peak keeps climbing is a 2.7 MB `index` chunk and a 2.0 MB `export-game` chunk
(the latter embeds the whole HTML player). The cap buys headroom; it does not buy a smaller
app. If a host ever caps build memory below ~1.3 GB, code-splitting those is the fix rather
than another number in the build script.

## Breaking changes / migration

None.
