# 0.8.220 — the other eight clouds (2026-08-25)

## Highlights
- Eight more shapes were drawing outside their own bounding box — the same defect that made cloud pattern fills stop in a flat line in 0.8.219, on shapes nobody had reported yet. All fixed, and a test now covers every shape so the next one cannot ship.

## Fixes

**#326 — Eight more shapes drew outside their own bounding box.**

The cloud was fixed in 0.8.219 as one shape. It was never one shape. "Draws outside its own box" is a whole class of bug, and an almost invisible one, because *drawing* the shape looks perfect — what breaks is everything downstream that trusts the shape's declared size: the pattern, mesh and image fills rasterise a buffer the size of the box and stop dead where it runs out, and the selection handles draw a rectangle through the middle of the artwork. Solid fill hides all of it, which is exactly why this arrived as a *fill* bug about a cloud.

An audit across every shape at four aspect ratios found eight more:

| shape | outside its box | cause |
| --- | --- | --- |
| `gauge` | 30.0% | `Math.min(w / 2, h * 0.8)` — `h * 0.8` is not a half-height |
| `lightbulb` | 16.7% | arc radius too small for its chord, so SVG inflates it (spec F.6.6) |
| `magnet` | 15.0% | the U's bend radius came from the width alone |
| `scroll` | 11.3% | the rolled ends curled outward from a full-width sheet |
| `chainLink` | 5.0% | corner radius exceeded the link's own width |
| `flag` | 2.4% | the wave's control point lifted the banner above the pole |
| `externalEntity` | 1.3% | the offset shadow was full size, so the pair overflowed |
| `handPointRight` | 1.0% | the closing curve's control point sat left of the edge |
| `burstBlob` | 0.6% | spikes varied *outward*, and `(w / h)` was used as a scale factor |

Each shape still looks like itself — verified by rendering every one against its box, not just by watching the numbers.

`chainLink`'s cause was shared and is now fixed at source: `getRoundedRectPath` never clamped its radius, so a radius wider than the box put `x + w - r` to the *left* of `x + r` and turned the rectangle inside out. No caller expected to have to think about that.

`burstBlob` also changes shape slightly for the better: it now fills a wide or tall box properly, where a stray `(w / h)` factor used to stretch it out through the side.

## Internal / tests / docs

- `shape-box-fit.test.ts` is the gate. It reads the element-type union directly, so a shape added next month is covered without anyone remembering to list it, and it asserts **both** directions — inside the box, and still reaching its edges, since shrinking every shape would also technically "fit".
- `puzzlePiece` and the 3D solids (`solidBlock`, `perspectiveBlock`, `openBox`, `isometricCube`) are outside their boxes *on purpose* and are exempt with stated reasons: a puzzle piece whose tabs stopped at the box would not interlock with the piece beside it, and a solid's extruded depth is drawn beside the front face the box describes. The test requires a reason for every exemption.
- The audit's own sampler carries eight tests of its own that run before any shape is judged. Its first draft skipped the arc's x-axis-rotation parameter and reported the `cylinder` as 562% oversized — the cylinder is fine, its arcs are rotated 90°, so `rx` and `ry` swap. A measuring tool that is confidently wrong is worse than none.

## Known limitation

The buffer-backed fills (pattern, mesh, image) still size themselves to the element's box rather than to the shape's real extent. For the shapes fixed above that no longer matters, but it means a **pattern or image fill on a `puzzlePiece` leaves its tabs unfilled**, and the same applies to the 3D solids. Fixing the fills rather than the shapes is the next piece of this work.

## Breaking changes / migration

- None. Nine shapes change proportions slightly to fit the box they are drawn in; existing documents re-render with the corrected geometry.
