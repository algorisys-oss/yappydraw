# 0.8.141 — Cropping a rotated image no longer moves it (2026-07-21)

## Highlights
- Cropping a **rotated** image kept the region in the wrong place — **76px off at 45°** for a
  400×200 image. Now exact.

## Fixes
- Bug #205: **crop ignored the element's rotation.** A crop rect is expressed in the element's own
  unrotated frame, but both places that repositioned the element from it — the apply path and the
  temporary "show the whole image" expansion added in 0.8.139 — added the offset directly to
  `x`/`y`. That is only correct at 0°; at any other angle the image jumped, further the more it was
  rotated.

  Both now turn the offset by the element's angle before applying it. Measured drift at 45°:
  **76.5px → 0.0px**.

## Internal / tests / docs
- New test covers a rotated crop end to end, computing where the kept region *should* land from the
  rotation and asserting the element centre matches within 1px.
- **Undo/redo for crop is confirmed working** and now asserted: undo restores the uncropped frame
  and position, redo re-applies exactly. Entering and cancelling crop mode leaves no phantom undo
  step — the temporary expansion is an editing affordance, not an edit, so it is applied without
  history.
- A measurement error caught on the way: the first run of this test set `angle: 45` assuming
  degrees. `angle` is in **radians** (`api.ts` says so). The corrected run produced the same drift,
  so the conclusion held — but the expectation had been computed for the wrong rotation.

## Breaking changes / migration
- None.
