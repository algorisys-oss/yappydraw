# 0.8.168 — Ctrl+A gives you a selection you can actually use (2026-07-31)

## Highlights
- **Select-all now arms the selection tool.** With a brush (or any drawing tool) active, `Ctrl+A`
  drew a selection box around everything and left you unable to touch it: clicking a selected
  shape didn't grab it, dragging painted another stroke, and no handle responded. The selection
  was real but inert, because every direct-manipulation path in the app is gated on the selection
  tool.
- **`app-store.test.ts` had not been running at all** — it threw at import and `bun test` counted
  that as an "error", not a failure, so a suite with a dead file still read as green. Suite goes
  **389 → 393**.

## Fixes
- **`selectAll()` switches to the selection tool when a drawing tool is active.** It previously
  wrote `store.selection` and nothing else. Dragging/resizing/marquee (`selectionOnDown`,
  `canvas.tsx:1678`) and control points, path anchors and connector handles
  (`selection-renderer.ts:621,664,675`) are all gated on `selectedTool === 'selection'`, so with a
  brush armed the selection could only be reached through the keyboard and the property panel.
- **The stale-selection half of the bug.** Brushes are in `CONTINUOUS_TOOLS`
  (`draw-handler.ts:68`), so the post-stroke branch that normally reassigns the selection is
  skipped entirely. A `Ctrl+A` selection therefore stayed painted over the canvas while the user
  kept drawing and silently went stale — it never contained the strokes drawn after it.
- **`lasso` keeps its tool** — it is already selection-capable and handles marquee and drag on the
  same code path. Only genuinely non-selection tools are switched away from.
- **An empty canvas leaves the active tool alone**, so the shortcut can never yank a brush out of
  someone's hand for no gain.
- Fixed in the store action rather than the `Ctrl+A` key handler, so the two context-menu
  "Select all" entries (`context-menu-builder.ts:332`, `:1562`) get the identical behaviour
  instead of drifting from the shortcut.

## Internal / tests / docs
- **Ordering trap, recorded:** `setSelectedTool` clears `store.selection` when switching to a
  drawing tool (`app-store.ts:1410`), so the tool switch must happen *before* the selection is
  written. The reverse order quietly select-alls into an empty selection.
- **Root `tsconfig.json` now mirrors `jsx`/`jsxImportSource` from `tsconfig.app.json`.** Bun
  resolves JSX from the *nearest* `tsconfig.json`; the root config is solution-style
  (`"files": []` + `references`) and carries no `compilerOptions`, so any `.tsx` reached
  transitively from a test — here `config/ui-shape-defs.tsx` — compiled against the React runtime
  and died on `Cannot find module 'react/jsx-dev-runtime'`. `tsc -b` builds only the referenced
  projects, so the build is unaffected.
- `app-store.test.ts` +3 cases: drawing tool switches, lasso is preserved, empty canvas is a
  no-op. Written first and confirmed red on the brush case before the fix.
- Help updated on both surfaces: the hotkey label in `help-dialog.tsx` and the `Ctrl+A` tip in
  `help-docs/features/bulk-editing-doc.tsx` (which now names `7`, the freehand brush shortcut, for
  getting back to drawing — `B` is the bezier tool).
- `docs/bugs/bug-fixes.md` #243; `docs/learnings.md` gains the general rule (a command that
  produces a selection must also produce the ability to use it) and the `bun test` error-vs-failure
  note.

## Breaking changes / migration
None for the API — `selectAll` is not exposed on `window.Yappy`. Interactively, `Ctrl+A` and the
context-menu "Select all" now leave you in the selection tool; press your tool's shortcut (`7` for
the freehand brush) to resume drawing.
