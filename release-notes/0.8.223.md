# 0.8.223 — reordering a layer now reorders the layer (2026-08-25)

## Highlights
- **Layer reordering has never changed what draws on top.** The panel moved the row and the canvas carried on painting in the old order. Fixed, along with the drag itself: a ghost of the row now follows the pointer, and an insertion line shows exactly where it will land.

## Fixes

**#331 — Reordering a layer moved it in the panel and nowhere else.**

Dragging a layer up the stack rearranged the Layers panel and left the drawing untouched. Two overlapping rectangles on two layers: move the lower layer to the top, and the panel shows it on top while the canvas still draws it underneath.

`reorderLayers` splices the array and then renumbers each layer's `order`. The renumbering was written as `layer.order = idx` over entries taken from `store.layers` — solid-js/store proxies, whose set trap is `set() { return true }`. Accepted and discarded, in both the dev and production store builds. So the array moved and `order` did not, and had not for as long as the function has existed.

That mattered because `order` is what stacks the document. `canvas-renderer` sorts by it before painting; so do hit-testing, the animation timeline, recording, timelapse and slide builds. Only the Layers panel looked right, and only by accident — it reverses the array rather than reading `order`. Every consumer that decides what is actually on top disagreed with the one surface the user was looking at.

`reorderedLayers` is now a pure function returning fresh objects, so nothing depends on the store accepting a mutation, and a document opened from a build that had the bug is normalised on load — the array is what its author was shown, so it wins.

The browser had been reporting this the whole time: one `Cannot mutate a Store directly` per layer per drag, in the console, unread.

**#330 — No drag preview when reordering layers.**

0.8.221 moved layer reordering from HTML5 drag-and-drop to pointer events, which removed the whole class of bug behind the no-entry cursor. It also removed something worth keeping: the browser renders a drag image automatically for a drag-and-drop, and a pointer drag has to draw its own. What was left was a dimmed source row and a highlighted target — and on a long list the dimmed row is often scrolled out of sight, so there was nothing telling you *what* you were carrying.

A ghost of the row now follows the pointer: its grip, its colour tag if it has one, and its name. It is offset from the cursor so it does not cover the row you are aiming at, `pointer-events: none` so it can never become its own drop target, and `position: fixed` so the panel's own overflow does not clip it while you drag past the ends of the list.

## Features

**An insertion line, instead of a highlighted row.** A highlighted target answers "swap with this one". The question you are actually asking on a long list is "where will it land", and a line between two rows answers it exactly: the top half of a row inserts above it, the bottom half below it. A group row in Groups mode keeps a third option — its outer quarters insert beside it, its middle drops into it, shown as a dashed outline rather than a line.

It also settles an inconsistency inside one panel: the **object tree** — the list you get from a layer's box icon — has always worked this way (`object-tree.tsx` splits each row at its midpoint into `drop-above`/`drop-below`), and the layer rows above it did not. Same panel, same gesture, two different answers.

This is what turned #331 up. A vague target can't be caught being wrong; a line that says *precisely* where the layer will land can, and it was — with Groups switched on, where the panel sorts by `order` rather than by array position, the layer visibly refused to move. The imprecise version had been hiding the bug, since d84ce04d on 2026-01-11 — the commit that introduced the layer system — by never making a checkable claim.

## Internal / tests / docs

- `frontend/src/store/layer-reorder.test.ts` pins the reorder. It is deliberately not written the obvious way, and the reason is worth recording: under `bun test` there is no `browser` export condition, so solid-js/store resolves to its **server** build, where a store is a plain object with no proxy and the direct write succeeds. The first version of this test drove the real store and asserted the resulting order — 7 green against code that was broken in every browser. The environment that should have caught this is the one place the bug does not reproduce. The tests that shipped assert instead that `reorderedLayers` leaves its input alone, which holds under both builds and fails under both against the old code.
- Help: the Layers section documents the ghost, the insertion line, and the into-group band.

## Breaking changes / migration

- Documents saved by an earlier build may carry a layer `order` that disagrees with the layer array — the reorder moved one and not the other. They are normalised when opened, taking the array as the truth because that is the order the Layers panel displayed. A document whose layers were reordered in an older build may therefore open with its stacking corrected to what the panel had been showing.
