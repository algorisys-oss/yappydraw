# Release Notes - v0.27.9

**Release Date:** May 6, 2026

## Overview

The real fix for iPad/Apple Pencil "alternate empty strokes" after seven prior attempts. Diagnosed via the user pointing to https://github.com/shuding/apple-pencil-safari-api-test, which works perfectly on iPad+Pencil and uses **TouchEvents** (not PointerEvents).

## What Was Wrong

iPad Safari's PointerEvent delivery for Apple Pencil is unreliable on rapid lift+recontact. The OS swallows alternate `pointerdown` events while it checks for system gestures (Apple Pencil double-tap, etc.). All previous attempts (palm-rejection heuristics, history snapshot optimization, capture try/catch, RAF flag reset, pointermove recovery) tried to work around this from the JavaScript side and either masked or partially mitigated the symptom — but none could fully fix it because the events simply weren't reaching the page.

TouchEvents go through reliably. Apple's own Pencil Safari API surfaces pen data through TouchEvents (`force`, `touchType: 'stylus'`, `altitudeAngle`, `azimuthAngle`).

## The Fix

For pen-drawing tools (fineliner, inkbrush, marker, ink), bind native TouchEvent listeners on the canvas with `passive: false` and drive strokes from them:

```ts
canvasRef.addEventListener('touchstart', handleTouchStart, { passive: false });
canvasRef.addEventListener('touchmove', handleTouchMove, { passive: false });
canvasRef.addEventListener('touchend', handleTouchEnd, { passive: false });
canvasRef.addEventListener('touchcancel', handleTouchEnd, { passive: false });
```

The handlers:
- `touchstart` → `preventDefault()`, set `touchDrivingPenStroke = true`, call `drawOnDown` with the touch's coordinates.
- `touchmove` → push to `penPointsBuffer`, schedule RAF flush.
- `touchend` / `touchcancel` → flush buffer, `drawOnUp`, clear flag.

A `touchDrivingPenStroke` flag tells the existing PointerEvent handlers to short-circuit cleanly. iOS fires both event families for the same physical contact, so without the flag they'd double-process.

For non-drawing tools (selection, pan, eraser, shapes, text, etc.) and desktop mouse, PointerEvents continue to drive everything — no behavioral change.
