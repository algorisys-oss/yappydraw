# Release Notes - v0.27.7

**Release Date:** May 6, 2026

## Overview

Defensive hardening for the iPad / Apple Pencil "every other character empty" issue that persisted past v0.27.4 and v0.27.6. Three independent failure modes all trigger only on **rapid pen lift + re-contact** between strokes, and each one alone is enough to drop a stroke. This release closes all three.

## Three Failure Modes Fixed

### 1. `setPointerCapture` throwing on iPad

When the previous stroke's pointer hasn't been fully released by the iOS pointer-event subsystem and the next `pointerdown` fires very quickly after, calling `setPointerCapture(newPointerId)` can throw `InvalidStateError`. A thrown exception inside an event handler **aborts the rest of the handler** — so `drawOnDown` never runs, no element is created, and the next move/up events have nothing to attach to. The stroke disappears.

Wrapped both `setPointerCapture` and `releasePointerCapture` in try/catch. The browser handles capture-less events fine; we'd rather lose pointer capture than abort the handler.

### 2. Palm rejection's 700 ms grace window blocking legitimate Pencil downs

v0.27.1 introduced a 700 ms post-pen window during which any `pointerType: 'touch'` event was rejected. The intent was palm rejection. The unintended consequence: iPad Safari occasionally reclassifies a rapid Apple Pencil tap as a `touch` event (with `pressure > 0` and a tiny contact area), and the v0.27.4 width heuristic didn't catch every such case (some events ship with `width: 0` or no width at all).

Dropped the time window entirely. We now only filter touch when a pen is **currently** in contact (`activePenPointerId !== null`), not "was recent". This relies on iPadOS's system-level palm rejection (which is excellent for paired Apple Pencils) as the primary defense; the JS check just covers the during-stroke case where palm contact could otherwise interfere with an in-flight pen stroke.

### 3. `penUpdatePending` RAF flag stuck between strokes

The pen handler schedules a `requestAnimationFrame` flush per pointermove. If a stroke ends before its RAF fires, `penUpdatePending` stays `true`. The next stroke's first pointermove sees `pending: true` and skips scheduling its own RAF. The data isn't lost — when the stale RAF eventually fires it flushes whatever's currently in the buffer to the new `currentId` — but the visual update can lag. Reset the flag to `false` on every `pointerdown` so each stroke starts with a clean RAF state.

## Why It Took Four Tries

Each version legitimately fixed one cause:

| Version | Fix                                                              | Did it solve the symptom? |
| ------- | ---------------------------------------------------------------- | -------------------------- |
| 0.27.4  | `isPencilSizedTouch` heuristic for misclassified Pencil          | Partial — caught some cases |
| 0.27.6  | Structural-share history snapshot (replace JSON deep clone)      | Partial — main thread freer but not enough |
| 0.27.7  | try/catch on capture + drop 700ms window + reset RAF flag        | (testing)                 |

Multiple independent issues were stacking. v0.27.4 and v0.27.6 each removed a contributing cause; each was strictly correct as a fix but neither alone restored full reliability. The defensive triple in v0.27.7 covers the remaining gaps.

## Key Files Modified

- `frontend/src/components/canvas.tsx` — try/catch on `setPointerCapture` / `releasePointerCapture`; loosened palm-rejection to "active pen only"; reset `penUpdatePending` and clear `penPointsBuffer` on every `pointerdown`
- `package.json` — version bump to 0.27.7
